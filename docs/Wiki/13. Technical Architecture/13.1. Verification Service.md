## Introduction
The VerificationService component is a core module within the Verity application responsible for validating file integrity by comparing computed cryptographic hashes against expected values stored in a manifest file. It supports multiple hash algorithms including SHA256, MD5, and SHA1, and is designed for high-performance execution through parallel processing. The service implements a producer-consumer pattern using `Channel<T>` for efficient work distribution across threads, supports cancellation via `CancellationToken`, and provides real-time progress reporting through event-driven notifications. This document details its internal architecture, data models, integration points, and operational behavior.

## Core Components
The VerificationService relies on several key components to perform its function:
- **VerificationJob**: Encapsulates a unit of work containing file metadata and expected hash.
- **VerificationResult**: Represents the outcome of a verification operation, including status and diagnostic details.
- **FinalSummary**: Aggregates results from all processed files into a comprehensive report.
- **FileStarted/FileProgress/FileCompleted events**: Enable real-time progress tracking.
- **FileIOUtils**: Provides optimized I/O operations for reading file data.
- **GlobUtils**: Handles file filtering based on include/exclude patterns.

These components work together to enable scalable, efficient, and observable file integrity verification.

## Architecture Overview
The VerificationService employs a concurrent producer-consumer architecture to maximize throughput while maintaining memory efficiency. A bounded channel distributes work items (VerificationJob) to multiple consumer tasks, which process files in parallel. Results are collected through an unbounded channel and aggregated into a final summary. This design enables the service to saturate available CPU and I/O resources without overwhelming system memory.

## Detailed Component Analysis

### VerificationJob and VerificationResult Models
The `VerificationJob` and `VerificationResult` records serve as the primary data carriers within the verification pipeline. `VerificationJob` contains the file's expected hash and relative path, along with its size, enabling pre-allocation and progress tracking. `VerificationResult` captures the outcome of the verification, including actual hash, status, and error details.

```
csharp
public record VerificationJob(
    ChecksumEntry Entry,
    long FileSize
);

public record VerificationResult(
    ChecksumEntry Entry,
    ResultStatus Status,
    string? ActualHash = null,
    string? Details = null,
    string? FullPath = null,
    Exception Exception = null
);

```

These immutable data structures ensure thread-safe sharing across tasks and provide clear contracts between components.

### Event-Driven Progress Reporting
The service uses four events to communicate progress and findings:
- **FileStarted**: Triggered when processing begins on a file.
- **FileProgress**: Fired periodically during file reading to report bytes processed.
- **FileCompleted**: Raised upon completion of a file's verification.
- **FileFoundNotInChecksumList**: Notifies when a file exists but is not listed in the manifest.

These events allow the UI layer (via Spectre.Console) to display live progress bars and diagnostics.

## Processing Flow
The verification process follows a structured workflow:
1. **Initialization**: Configure parallelism, root path, and channels.
2. **Production**: Enumerate manifest entries and write jobs to the channel.
3. **Consumption**: Parallel tasks read jobs, compute hashes, and publish results.
4. **Post-Verification Scan**: Identify files present in the directory but missing from the manifest.
5. **Aggregation**: Collect all results and generate a summary.

The producer task reads file sizes upfront to enable accurate progress reporting, while consumers use asynchronous file streams and pooled buffers to minimize memory allocation.

## Error Classification Logic
The service classifies outcomes into three distinct states:
- **Success**: Computed hash matches the expected value.
- **Warning**: Hash mismatch occurs, but the file was modified after the manifest was created (indicating a potential update).
- **Error**: Hash mismatch with an older file, or file access failure.

This logic prevents false positives when files have been legitimately updated. The classification is implemented in the `StatusClassifier` static class, which compares file timestamps against the manifest timestamp.

## Performance Considerations
The service incorporates several optimizations for performance and resource efficiency:

### I/O Buffer Sizing
The `FileIOUtils.GetOptimalBufferSize` method dynamically selects buffer sizes:
- **Small files (<64KB)**: 4KB buffer
- **Large files (≥64KB)**: 1MB buffer

This reduces system call overhead for large files while avoiding excessive memory use for small ones.

```
csharp
public static int GetOptimalBufferSize(long fileSize)
{
    const int smallFileThreshold = 64 * 1024;
    const int defaultBufferSize = 4096;
    const int largeFileBufferSize = 1 * 1024 * 1024;
    return (fileSize > smallFileThreshold) ? largeFileBufferSize : defaultBufferSize;
}

```

### Memory Management
- Uses `ArrayPool<byte>.Shared` to rent and return buffers, reducing GC pressure.
- Processes files sequentially within each consumer to limit concurrent memory usage.
- Employs `IncrementalHash` for streaming hash computation without loading entire files into memory.

### Parallelism
- Default parallelism equals the number of CPU cores.
- Bounded job channel prevents overwhelming the system with pending work.
- Unbounded result channel ensures no blocking during result collection.

## Integration with Program Entry Point
The VerificationService is invoked from the `verify` command in `Program.cs`. The command parses CLI options, reads the manifest, and initializes the service with appropriate parameters. Event handlers are attached to integrate with Spectre.Console's progress display system, creating a responsive user interface.

```
csharp
var verificationService = new VerificationService();
verificationService.FileStarted += (sender, e) => {
    var task = ctx.AddTask(e.Entry.RelativePath, maxValue: e.FileSize);
    e.Bag = task;
};
// ... other event handlers
summary = await verificationService.VerifyChecksumsAsync(options, manifestEntries, threads, cancellationToken);

```

The service returns a `FinalSummary` object used to render results and determine the process exit code (0=success, 1=warnings, -1=errors).

## Volume Shadow Copy Service Integration
The VerificationService now supports Volume Shadow Copy Service (VSS) integration for accessing files that may be locked or in use. This feature enables verification of system files and other resources that are typically inaccessible during normal operation.

### VssPathResolver Implementation
The `VssPathResolver` class translates original file paths to their corresponding VSS snapshot paths. It maintains two key properties:
- **SnapshotPath**: The device path provided by VSS (e.g., `\\?\GLOBALROOT\Device\HarddiskVolumeShadowCopy1`)
- **OriginalVolumeRoot**: The original volume root that was snapshotted (e.g., `C:\`)

```
csharp
public class VssPathResolver
{
    public string SnapshotPath { get; }
    public string OriginalVolumeRoot { get; }
    
    public string ResolvePath(string originalPath)
    {
        var fullOriginalPath = Path.GetFullPath(originalPath);
        if (!fullOriginalPath.StartsWith(OriginalVolumeRoot, StringComparison.OrdinalIgnoreCase))
        {
            return fullOriginalPath; // Path not on snapshotted volume
        }
        
        var relativePath = fullOriginalPath.Substring(OriginalVolumeRoot.Length);
        return Path.Combine(SnapshotPath, relativePath);
    }
}

```

### Service Integration
The VerificationService exposes a `VssResolver` property that, when set, redirects file operations through the VSS snapshot:

```
csharp
public VssPathResolver? VssResolver { get; set; }

// In file processing:
var effectivePath = VssResolver?.ResolvePath(fullPath) ?? fullPath;
using (var stream = new FileStream(effectivePath, FileMode.Open, FileAccess.Read, FileShare.Read, bufferSize, FileOptions.Asynchronous))
{
    // Process file from snapshot
}
```

### Usage Workflow
1. Create a `VssSnapshotManager` instance for the target volume
2. Create the snapshot using `CreateSnapshotAsync()`
3. Obtain a `VssPathResolver` via `CreatePathResolver()`
4. Assign the resolver to the VerificationService
5. Execute verification operations
6. Dispose of the snapshot manager to clean up resources

This integration allows the Verity application to verify the integrity of critical system files without requiring exclusive access or system downtime.
