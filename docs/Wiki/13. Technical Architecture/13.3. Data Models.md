## Introduction
This document provides comprehensive documentation for the core data models defined in Models.cs for the Verity application. Verity is a file integrity verification tool that uses checksum manifests to validate file contents. The data models serve as the foundation for configuration, processing, and reporting throughout the application. These models are designed as immutable records to ensure thread safety in parallel operations and to provide structural equality for reliable comparisons. The document details each model's properties, semantics, and usage patterns across the application, from command-line parsing to final reporting.

## Core Data Models Overview
The Verity application defines five primary data models that form the backbone of its data processing pipeline. These models are implemented as C# records, providing immutability, structural equality, and concise syntax. The models work together to represent configuration options, manifest entries, processing units, verification outcomes, and aggregated results. They serve as data transfer objects (DTOs) between the application's entry point (Program.cs), core services (VerificationService, ManifestCreationService), and utility components (ResultsPresenter, ManifestReader, ManifestWriter). ## CliOptions Model
The CliOptions model represents the command-line configuration for the Verity application. It is a record struct that captures all user-specified options when running the application. The model is instantiated in Program.cs from command-line arguments and serves as the primary configuration object passed to various services.

### Property Semantics
- **ChecksumFile**: [FileInfo] The manifest file containing checksums. This is a required parameter and determines the primary input for verification or creation operations.
- **RootDirectory**: [DirectoryInfo?] The root directory for resolving file paths. If not specified, defaults to the manifest file's directory.
- **Algorithm**: [string] The hashing algorithm to use (e.g., SHA256, MD5). Inferred from the manifest file extension if not explicitly provided.
- **TsvReportFile**: [FileInfo?] Optional output file for machine-readable TSV error reporting. Defaults to null.
- **ShowTable**: [bool] Flag to force display of the diagnostic table even when no issues are found. Defaults to false.
- **IncludeGlobs**: [string[]?] Array of glob patterns for files to include. Defaults to null (include all files).
- **ExcludeGlobs**: [string[]?] Array of glob patterns for files to exclude. Defaults to null (exclude nothing).
- **UseVss**: [bool] Flag to enable Volume Shadow Copy Service for accessing locked files. Requires administrator privileges. Defaults to false.

### Default Values and Validation
The model uses C#'s default parameter values for optional fields. Validation occurs in Program.cs before instantiation, with null checks and file/directory existence verification. The algorithm is validated against supported hashing algorithms when used by services. When UseVss is set to true, the application checks for elevation privileges and will attempt to restart with elevated permissions if necessary.

## ChecksumEntry Model
The ChecksumEntry model represents a single line item in a checksum manifest file. It is a simple record that contains the expected hash value and the relative path of a file.

### Property Semantics
- **ExpectedHash**: [string] The expected hash value for the file, typically stored in hexadecimal format.
- **RelativePath**: [string] The relative path of the file from the root directory, used to locate the file during verification.

### Usage in Manifest Processing
This model is used by both ManifestReader and ManifestWriter to represent manifest entries. The ManifestReader parses TSV lines into ChecksumEntry objects, while the ManifestWriter formats ChecksumEntry objects into TSV lines. The model's simplicity makes it ideal for serialization and deserialization.

## VerificationJob Model
The VerificationJob model represents a unit of work for the file verification process. It combines a ChecksumEntry with additional metadata needed for processing.

### Property Semantics
- **Entry**: [ChecksumEntry] The manifest entry containing the expected hash and relative path.
- **FileSize**: [long] The size of the file to be verified, determined before processing begins.

### Role in Parallel Processing
This model serves as the input to the verification pipeline. VerificationService creates VerificationJob instances for each manifest entry and processes them in parallel. The file size is pre-fetched to enable progress tracking in the user interface.

## VerificationResult Model
The VerificationResult model represents the outcome of verifying a single file. It extends the ChecksumEntry with status information and diagnostic details.

### Property Semantics
- **Entry**: [ChecksumEntry] The original manifest entry being verified.
- **Status**: [ResultStatus] Enumeration indicating the result status (Success, Warning, Error).
- **ActualHash**: [string?] The actual hash computed during verification, null on failure.
- **Details**: [string?] Human-readable explanation of the result, particularly for warnings and errors.
- **FullPath**: [string?] The absolute path of the file, resolved from the relative path.
- **Exception**: [Exception] Any exception encountered during verification, captured for debugging.

### Status Classification
The ResultStatus enum provides three levels of outcome:
- **Success**: File hash matches expected value.
- **Warning**: Potential issue detected (e.g., file modified after manifest creation).
- **Error**: Verification failed (e.g., hash mismatch, file not found).

## FinalSummary Model
The FinalSummary model represents aggregated statistics from a verification or manifest creation operation.

### Property Semantics
- **TotalFiles**: [int] Total number of files processed.
- **SuccessCount**: [int] Number of files that verified successfully.
- **WarningCount**: [int] Number of files with warnings.
- **ErrorCount**: [int] Number of files with errors.
- **TotalBytesRead**: [long] Total number of bytes processed.
- **ProblematicResults**: [IReadOnlyList<VerificationResult>] List of all non-success results for detailed reporting.

### Aggregation Strategy
The model collects only problematic results (warnings and errors) to minimize memory usage, as successful results are typically not needed for reporting. This design choice reflects the application's focus on identifying and reporting issues.

## Immutability and Thread Safety
The use of C# records for all core models provides several important benefits for the Verity application, particularly in the context of parallel processing.

### Benefits of Records
- **Immutability**: Once created, record instances cannot be modified, preventing unintended state changes.
- **Structural Equality**: Records automatically implement value-based equality, allowing reliable comparison of model instances.
- **Thread Safety**: Immutable objects are inherently thread-safe, eliminating race conditions in parallel operations.
- **Concise Syntax**: Records reduce boilerplate code for constructors, properties, and equality members.

### Impact on Parallel Operations
In VerificationService, multiple threads process VerificationJob instances simultaneously. The immutability of these models ensures that shared data cannot be corrupted. When VerificationResult instances are created, they are immutable snapshots of the verification outcome, safe to collect and aggregate from multiple threads.

## Pattern Matching and Deconstruction
The ResultsPresenter utility demonstrates sophisticated use of pattern matching and deconstruction to format output based on model data.

### Status-Based Formatting
The RenderDiagnosticsTable method uses pattern matching on the ResultStatus property to determine color-coded output:


```csharp
var statusMarkup = result.Status switch {
    ResultStatus.Warning => "[yellow]Warning[/]",
    ResultStatus.Error => "[red]Error[/]",
    _ => "[grey]Info[/]"
};
```


### Deconstruction in Reporting
The WriteErrorReportAsync method deconstructs VerificationResult instances to extract values for TSV serialization:


```csharp
string.Join("\t",
    result.Status.ToString().ToUpperInvariant(),
    result.FullPath ?? result.Entry.RelativePath,
    result.Details ?? "",
    result.Entry.ExpectedHash,
    result.ActualHash ?? ""
)
```


This approach provides clean, readable code for transforming model data into various output formats.

## Serialization and Reporting
The models are designed with serialization in mind, particularly for TSV reporting.

### TSV Reporting Format
The WriteErrorReportAsync method in ResultsPresenter generates a machine-readable TSV report with the following structure:
- Header: #Status\tFile\tDetails\tExpectedHash\tActualHash
- Data rows: Status, FullPath, Details, ExpectedHash, ActualHash (tab-separated)

### Serialization Considerations
- **Null Handling**: Optional fields are safely handled with null-coalescing operators.
- **Case Consistency**: Status values are converted to uppercase for consistency.
- **Path Resolution**: FullPath is preferred, with RelativePath as fallback.
- **Encoding**: UTF-8 encoding is used to support international characters in file paths.

The design ensures reliable serialization while maintaining human readability.

## Extensibility Considerations
The current model design supports future enhancements while maintaining backward compatibility.

### Adding New Hash Algorithms
The Algorithm property in CliOptions is a string, allowing support for new algorithms without model changes. Services use HashAlgorithmName to validate and instantiate the appropriate hasher.

### Adding Metadata Fields
To add metadata to ChecksumEntry, consider:
- Creating a new record that inherits from ChecksumEntry (if using classes)
- Adding optional properties with default values
- Using a separate metadata dictionary for flexible extensibility

### Enhanced Reporting
Future versions could extend FinalSummary to include:
- Performance metrics per file
- Geographic location data for distributed systems
- Custom tags or categories for result filtering

The immutable record design ensures that such extensions can be made without breaking existing code that depends on the models.

### VSS Integration Extensibility
The VSS implementation provides a foundation for future enhancements:
- **Snapshot Configuration**: Future versions could add parameters for snapshot retention, differential vs full snapshots, or compression settings.
- **Multi-Volume Support**: The current implementation could be extended to handle multiple volumes or network shares.
- **Snapshot Management**: Additional utilities could be developed for listing, mounting, or browsing snapshots independently of verification operations.
