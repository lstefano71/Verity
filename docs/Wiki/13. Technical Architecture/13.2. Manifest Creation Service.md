## Introduction
The **ManifestCreationService** is a core component of the Verity application responsible for generating and updating cryptographic checksum manifests. These manifests are TSV-formatted files that record file paths and their corresponding hash values, enabling integrity verification of directory contents. The service supports two primary operations: `create` (initial manifest generation) and `add` (incremental updates). It is designed for efficiency, scalability, and robustness, handling large directory trees with concurrent file processing and optimized I/O operations.

## Core Responsibilities
The **ManifestCreationService** orchestrates the entire manifest creation and update process. Its primary responsibilities include:
- Scanning directory trees to identify files for processing
- Applying glob-based inclusion and exclusion rules to filter files
- Computing cryptographic hashes (e.g., SHA256, MD5) using streaming for memory efficiency
- Managing the lifecycle of manifest files (creation and updates)
- Handling relative and absolute path resolution
- Emitting progress events for monitoring and diagnostics
- Aggregating results and generating summary statistics
- Accessing files through Volume Shadow Copy Service (VSS) snapshots when requested

The service operates in two distinct modes:
- **Create Mode**: Generates a new manifest from scratch for a specified set of files.
- **Add Mode**: Loads an existing manifest, computes hashes for new files, merges entries, and writes the updated manifest.

## Workflow Overview
The workflow for both `create` and `add` operations is managed by the `ProcessManifestFilesAsync` method, which performs the following steps:
1. **File Enumeration**: Receives a list of file paths (full paths for `create`, relative paths for `add`).
2. **Concurrent Processing**: Partitions the file list and processes files in parallel using a configurable number of threads.
3. **Path Resolution**: If a VssResolver is configured, resolves the original file path to its VSS snapshot equivalent.
4. **Hash Computation**: For each file, opens a stream, reads data in chunks, and updates a cryptographic hash incrementally.
5. **Event Emission**: Fires `FileStarted`, `FileProgress`, and `FileCompleted` events to allow external components to track progress.
6. **Result Aggregation**: Collects successful hash computations and error details in thread-safe collections.
7. **Manifest Update**: In `add` mode, reads the existing manifest, merges new entries (avoiding duplicates), and writes the combined list.

## File Scanning and Filtering
File selection is governed by the **GlobUtils** class, which uses the `Microsoft.Extensions.FileSystemGlobbing` library to apply pattern matching. The service does not perform directory scanning itself; instead, it relies on higher-level components (like CLI commands) to provide the initial file list. However, `GlobUtils` is used to filter this list based on user-defined rules.

- **Include Globs**: Semicolon-separated patterns (e.g., `*.txt;*.log`). Defaults to `**/*` (all files) if not specified.
- **Exclude Globs**: Semicolon-separated patterns (e.g., `*.tmp;*.log`). Files matching these are omitted.
- **Case Insensitive**: Matching is performed with `StringComparison.OrdinalIgnoreCase`.

The `FilterFiles` method normalizes paths and uses a `Matcher` to efficiently determine which files from the input list should be processed.

## Hash Computation and Streaming
The service computes cryptographic hashes using .NET's `IncrementalHash` class, which allows for streaming computation without loading entire files into memory. This is critical for handling large files efficiently.

- **Buffer Management**: The `FileIOUtils.GetOptimalBufferSize` method determines the buffer size based on file size:
  - **Small files** (< 64KB): 4KB buffer
  - **Large files** (≥ 64KB): 1MB buffer
- **Asynchronous I/O**: Uses `FileStream` with `FileOptions.Asynchronous` and `ReadAsync` for non-blocking operations.
- **Memory Pooling**: Employs `ArrayPool<byte>.Shared` to rent and return byte buffers, minimizing garbage collection pressure.
- **Algorithm Flexibility**: Supports any algorithm available via `HashAlgorithmName` (e.g., SHA256, MD5, SHA1).

## Manifest File Management
Manifest files are stored in TSV (Tab-Separated Values) format, with each line containing a hash and a relative file path.

- **Writing**: The **ManifestWriter** class uses a `StreamWriter` with a lock (`_writeLock`) to ensure thread-safe writes. The `WriteAllEntriesAsync` method writes all entries in a single atomic operation within the lock, preventing interleaved writes from concurrent threads.
- **Reading**: The **ManifestReader** class parses the TSV file line by line using `File.ReadLinesAsync`. It splits each line on the tab character and creates `ManifestEntry` objects. Empty lines and lines without a tab are skipped.
- **Update Logic**: In `add` mode, the service reads the existing manifest, converts entries to a list of `(hash, relativePath)` tuples, and combines them with new entries. A `HashSet` is used to prevent duplicates based on case-insensitive path comparison.

## Path Handling and Metadata
The service carefully manages file paths to ensure consistency and portability.

- **Relative Paths**: All paths stored in the manifest are relative to a specified root directory. This is achieved using `Path.GetRelativePath(root.FullName, fullPath)`.
- **Root Directory**: The `root` parameter defines the base path for relative path calculation. This allows manifests to be portable and not tied to a specific absolute location.
- **Path Normalization**: The `GlobUtils.FilterFiles` method normalizes path separators (`/` and `\`) to the platform's default using `Path.DirectorySeparatorChar`, ensuring consistent matching.
- **Metadata**: While the manifest itself only stores hash and relative path, the service emits events (`ManifestFileStartedEventArgs`, `ManifestFileProgressEventArgs`, `ManifestFileCompletedEventArgs`) that include the full file path and file size, providing rich metadata for diagnostic tools.

## Duplicate and Update Logic
The service implements a robust strategy for handling duplicate files during `add` operations.

- **Detection**: When adding new files, the service first loads all existing entries from the manifest. It extracts the relative paths and stores them in a `HashSet<string>` with `StringComparer.OrdinalIgnoreCase`.
- **Filtering**: New entries are filtered using `!existingPaths.Contains(e.relativePath)`, ensuring that no file is added twice, even if its content has changed.
- **Ordering**: All entries (existing and new) are sorted by relative path before being written, ensuring a consistent and predictable manifest structure.
- **No Overwrite**: The current implementation does not update the hash of an existing file. To change a file's hash, the manifest must be recreated or the old entry manually removed.

This logic prevents manifest bloat and ensures that the `add` command is idempotent for the same set of files.

## Integration Points
The **ManifestCreationService** integrates with several key utilities to fulfill its responsibilities.

- **FileIOUtils**: Used to determine the optimal buffer size for file I/O operations based on file size, optimizing performance for both small and large files.
- **ResultsPresenter**: Consumes the `FinalSummary` object returned by the service to generate human-readable diagnostic output, including summary tables, detailed diagnostics, and error reports in TSV format.
- **VssPathResolver**: When VSS mode is enabled, the service uses this component to resolve original file paths to their VSS snapshot equivalents, allowing access to locked or in-use files.
- **Event Handlers**: The service's events (`FileStarted`, `FileProgress`, `FileCompleted`) allow external components (like CLI progress bars or logging systems) to react to file processing in real-time.

## Edge Case Handling
The service includes mechanisms to handle common edge cases:

- **Concurrent Modifications**: File reads are performed with `FileShare.Read`, allowing other processes to read the file simultaneously. However, if a file is modified during reading, the resulting hash may be inconsistent. The service does not lock files exclusively.
- **Permission Restrictions**: If a file cannot be read due to permission issues, a `VerificationResult` with `ResultStatus.Error` is added to the summary, and processing continues with other files.
- **Symbolic Links**: The service treats symbolic links as regular files. It will attempt to read the target file. If the target is inaccessible, it will result in a read error.
- **Missing Files**: Files that are deleted between enumeration and processing will cause a read exception, which is caught and reported as an error.
- **Large Directories**: The use of `Partitioner.Create` and parallel `Task.Run` ensures efficient utilization of multiple CPU cores for hashing many files.

The service prioritizes resilience, ensuring that a single file error does not halt the entire operation.

## VSS Integration and Path Resolution
The **ManifestCreationService** now supports Volume Shadow Copy Service (VSS) integration, enabling access to files that may be locked or in use by other processes.

- **VssPathResolver**: The service has a `VssResolver` property of type `VssPathResolver`. When set, this component is used to translate original file paths to their VSS snapshot equivalents.
- **Path Resolution**: The `ResolvePath` method in `VssPathResolver` takes an original file path and returns the corresponding path in the VSS snapshot by:
  1. Converting to full path
  2. Checking if the path is on the snapshotted volume
  3. Calculating the relative path from the volume root
  4. Combining with the snapshot device path
- **Integration Flow**: In the `ProcessManifestFilesAsync` method, the service checks if `VssResolver` is set. If so, it calls `ResolvePath` to get the snapshot path; otherwise, it uses the original path.
- **VssSnapshotManager**: This component (used by the application layer) creates VSS snapshots and provides the `VssPathResolver` instance to the service.
- **Elevation Requirements**: VSS operations require administrative privileges, which are handled by the `ElevationHelper` class in the application layer.

This integration allows the service to create manifests of files that would otherwise be inaccessible due to file locks, enhancing its utility in enterprise environments.
