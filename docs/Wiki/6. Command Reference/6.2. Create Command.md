## Command Overview

The `create` command generates a new checksum manifest from a directory of files, calculating cryptographic hashes for each file and writing the results in tab-separated values (TSV) format. This command serves as the primary method for establishing file integrity baselines for archival, distribution, or verification purposes.

When executed, the command recursively scans the specified directory (or the manifest's parent directory by default), applies include/exclude glob filters, computes hashes using the specified algorithm, and produces a manifest file where each line contains a hash and its corresponding relative file path. The process is designed to be efficient and scalable, handling large directory trees with optimal resource utilization.

A new feature in this command is the integration with Volume Shadow Copy Service (VSS), which allows the creation of manifests for files that may be locked or in use by other processes. When the `--vss` flag is used, the command creates a VSS snapshot of the volume, enabling access to files that would otherwise be unreadable.

The command integrates with the application's rich terminal interface, providing live progress updates, a summary table upon completion, and optional machine-readable error reporting. It returns distinct exit codes to facilitate automation: `0` for success, `1` for warnings (such as unreadable files), and `-1` for critical errors.

## Argument Reference

The `create` command supports several arguments and options that control its behavior:

**:outputManifest**
- **Description**: Specifies the path for the output manifest file.
- **Required**: Yes
- **Default**: None
- **Behavior**: The manifest will be created at this location. If the file already exists, it will be overwritten.

**:root**
- **Description**: Sets the root directory to scan for files.
- **Short form**: `-r`
- **Required**: No
- **Default**: The directory containing the output manifest file
- **Behavior**: All file paths in the manifest are relative to this root directory. When not specified, the parent directory of the output manifest is used.

**:algorithm**
- **Description**: Specifies the hashing algorithm to use.
- **Short form**: `-a`
- **Required**: No
- **Default**: Inferred from the manifest file extension (`.sha256`, `.md5`, `.sha1`), otherwise SHA256
- **Supported values**: `SHA256`, `MD5`, `SHA1`
- **Behavior**: Determines the cryptographic algorithm used for hash calculation. The choice affects security, performance, and compatibility.

**:threads**
- **Description**: Sets the number of parallel threads for file processing.
- **Short form**: `-t`
- **Required**: No
- **Default**: Number of logical processors on the system
- **Behavior**: Controls the degree of parallelism. Higher values can improve performance on multi-core systems and when reading from fast storage.

**:include**
- **Description**: Semicolon-separated glob patterns for files to include in the manifest.
- **Required**: No
- **Default**: `**/*` (all files)
- **Behavior**: Only files matching at least one include pattern are processed. Multiple patterns are separated by semicolons.

**:exclude**
- **Description**: Semicolon-separated glob patterns for files to exclude from the manifest.
- **Required**: No
- **Default**: None
- **Behavior**: Files matching any exclude pattern are omitted, even if they match an include pattern. Exclude patterns take precedence over include patterns.

**:tsv-report**
- **Description**: Path to write a machine-readable TSV error/warning report.
- **Required**: No
- **Default**: Report written to stderr if issues are found
- **Behavior**: When specified, all warnings and errors are written to this file in TSV format, enabling automated processing.

**:show-table**
- **Description**: Forces display of the diagnostic table even if no issues are found.
- **Required**: No
- **Default**: False
- **Behavior**: Ensures the detailed results table is always shown in the terminal output.

**:vss**
- **Description**: Creates a Volume Shadow Copy Service (VSS) snapshot to access locked files.
- **Short form**: `-vss`
- **Required**: No
- **Default**: False
- **Behavior**: When enabled, creates a VSS snapshot of the volume containing the root directory, allowing access to files that are locked or in use by other processes. Requires administrator privileges.
- **Security Note**: This option requires elevation (administrator privileges) to create VSS snapshots.

## File Enumeration and Filtering

File enumeration and filtering are handled through a coordinated process that begins with directory scanning and applies glob-based filtering to determine which files should be included in the manifest. The `FilesToAddAsync` method in `Program.cs` performs the initial file discovery by recursively enumerating all files in the root directory using `EnumerateFileSystemInfos`.

During enumeration, each file's relative path is calculated from the root directory. The `GlobUtils.IsMatch` method then evaluates whether the file should be included based on the provided include and exclude patterns. The filtering system supports semicolon-separated glob patterns, with `**/*` as the default include pattern (matching all files) and no default exclude patterns.

When VSS mode is enabled, the file enumeration still occurs on the original file paths, but the actual file reading is performed through the VSS snapshot, allowing access to locked files.

## Hashing Implementation

The hashing implementation uses .NET's `IncrementalHash` class to compute cryptographic hashes in a memory-efficient manner. For each file, the system creates a `FileStream` with asynchronous reading capabilities and an optimized buffer size determined by `FileIOUtils.GetOptimalBufferSize` based on the file size.

The `ProcessManifestFilesAsync` method in `ManifestCreationService` handles the hashing process, using `Task.WhenAll` with `Partitioner.Create` to distribute files across multiple threads. Each thread processes its assigned files independently, creating a hash context with the specified algorithm (SHA256, MD5, or SHA1) and streaming the file content in chunks.

When VSS mode is enabled, the `VssResolver` is used to translate the original file path to the corresponding path in the VSS snapshot, allowing the system to read files that may be locked or in use by other processes.

``mermaid

The implementation uses `ArrayPool<byte>.Shared` to rent and return byte buffers, minimizing garbage collection pressure. Hashes are computed incrementally as data is read, ensuring that even very large files can be processed without loading the entire file into memory. The final hash is converted to a lowercase hexadecimal string using `Convert.ToHexString`.

## Manifest Serialization

Manifest serialization is handled by the `ManifestWriter` class, which writes entries in the required TSV format with a tab separator between the hash and relative path. The class uses a `StreamWriter` with a 4KB buffer to efficiently write to the output file, and employs a lock to ensure thread safety when multiple threads attempt to write simultaneously.

The `ManifestWriter` provides two methods: `WriteEntryAsync` for writing individual entries and `WriteAllEntriesAsync` for writing all entries at once. The manifest creation process uses the bulk method, which first collects all hash results in a `ConcurrentBag` and then writes them in a single locked operation, sorted alphabetically by path.

## Performance Characteristics

The `create` command is designed with performance as a primary consideration, employing several optimization strategies to maximize throughput:

**:Parallel Processing**
The command uses a parallel processing model where files are partitioned across multiple threads (defaulting to the number of logical processors). This allows the application to saturate both CPU and I/O resources, particularly beneficial when reading from fast storage like SSDs.

**:Memory-Efficient Streaming**
Files are processed in a streaming fashion, with content read in chunks rather than loaded entirely into memory. The buffer size is dynamically optimized based on file size, balancing memory usage and I/O efficiency. The use of `ArrayPool<byte>.Shared` further reduces memory allocation overhead.

**:Batched I/O Operations**
Manifest writing is performed as a single batch operation after all hashes are computed, minimizing disk I/O operations and file system metadata updates. This approach is more efficient than writing each entry individually.

**:Efficient File Enumeration**
The implementation uses `EnumerateFileSystemInfos` rather than `GetFiles`, which is more memory-efficient for large directories as it returns an iterator rather than a complete list.

**:Algorithm Performance**
The choice of hash algorithm significantly impacts performance: SHA256 provides the strongest security but is slower, MD5 is fastest but cryptographically broken, and SHA1 offers a middle ground. Users should select the algorithm based on their security requirements and performance constraints.

**:VSS Performance Considerations**
When using VSS mode, there is additional overhead from creating the volume snapshot. This operation typically takes a few seconds but enables access to locked files. The actual file reading performance through VSS is comparable to normal file reading.

## Edge Cases and Error Handling

The `create` command includes robust handling for various edge cases and error conditions:

**:Empty Directories**
When the specified root directory contains no files (or no files matching the include/exclude filters), the command creates an empty manifest file and returns exit code 1 to indicate a warning condition. This behavior ensures the manifest file is created even when no content is available.

**:Unreadable Files**
If a file cannot be read (due to permissions, locking, or other I/O errors), the command records the failure in the results summary and continues processing other files. The problematic file is included in any TSV report with an "Cannot read file" error message.

**:Path Normalization**
The system normalizes path separators to ensure consistent representation across different operating systems. Relative paths use the platform-appropriate directory separator, and the `GlobUtils.Normalize` method ensures consistent comparison during filtering.

**:File System Boundaries**
The recursive scanning respects directory boundaries and does not cross into mounted volumes or symbolic links that point outside the root directory, preventing unintended file inclusion.

**:Concurrent Access**
The `ManifestWriter` uses a lock to prevent race conditions when multiple threads attempt to write to the manifest file simultaneously, ensuring data integrity.

**:Cancellation Support**
The entire process supports cancellation via `CancellationToken`, allowing users to interrupt long-running operations with Ctrl+C, which results in exit code -2.

**:VSS-Specific Error Handling**
- If VSS mode is requested without administrator privileges, the command automatically requests elevation.
- If the user declines elevation, the command exits with code 100 (`ElevationRequired`).
- If VSS snapshot creation fails, the command exits with code 102 (`SnapshotCreationFailed`).
- If the volume does not support VSS, the command exits with code 103 (`VolumeNotSupported`).

## Usage Examples

**:Basic Manifest Creation**
Create a manifest for all files in the current directory using the default SHA256 algorithm:

```
Verity.exe create manifest.sha256
```


**:Custom Root Directory**
Create a manifest for files in a specific directory, with the manifest stored elsewhere:

```
Verity.exe create D:\backups\archive\manifest.txt --root C:\data\project
```


**:Glob-Based Filtering**
Create a manifest containing only image files while excluding temporary files:

```
Verity.exe create images.sha256 --include "*.jpg;*.png;*.gif" --exclude "*.tmp;*.bak"
```


**:Multiple Threads for Performance**
Use 8 threads to accelerate manifest creation on a multi-core system:

```
Verity.exe create backup.sha256 --threads 8
```


**:Machine-Readable Error Reporting**
Create a manifest and write any issues to a TSV file for automated processing:

```
Verity.exe create data.md5 --tsv-report errors.tsv
```


**:Explicit Algorithm Selection**
Create a manifest using MD5 (despite the .txt extension) for compatibility with legacy systems:

```
Verity.exe create manifest.txt --algorithm MD5
```


**:VSS Mode for Locked Files**
Create a manifest for system files that may be locked by other processes (requires administrator privileges):

```
Verity.exe create system.sha256 --root C:\Windows\System32 --vss
```


## Best Practices

**:Use Appropriate File Extensions**
Use standard file extensions (.sha256, .md5, .sha1) to enable automatic algorithm detection and improve interoperability with other tools.

**:Store Manifests Separately**
Keep manifest files in a different location from the data they describe to prevent both from being lost in the same failure event.

**:Regular Manifest Updates**
For archival purposes, recreate manifests periodically to ensure they reflect the current state of files, especially when files may be modified.

**:Validate After Creation**
Always verify a newly created manifest immediately to confirm its integrity:

```
Verity.exe verify manifest.sha256
```


**:Use Strong Algorithms for Security-Critical Applications**
Prefer SHA256 over MD5 or SHA1 for applications requiring cryptographic security, as MD5 and SHA1 are vulnerable to collision attacks.

**:Optimize Thread Count**
Adjust the `--threads` parameter based on your storage system; use higher values for SSDs and lower values for HDDs to avoid I/O thrashing.

**:Include in Automation Workflows**
Integrate manifest creation into backup and deployment scripts to automatically establish integrity baselines for critical data.

**:Use VSS for System Files**
When creating manifests for system directories or files that may be locked, use the `--vss` flag to ensure all files can be accessed.

**:Handle Elevation Requirements**
When using VSS mode in automated scripts, ensure the script is run with appropriate privileges or can handle the elevation prompt.

## VSS Integration and Elevation Handling

The `create` command now supports Volume Shadow Copy Service (VSS) integration through the `--vss` flag, enabling the creation of manifests for files that are locked or in use by other processes.

**:VSS Workflow**
1. When the `--vss` flag is specified, the command checks if it has administrator privileges.
2. If not elevated, it automatically requests elevation through Windows UAC.
3. Once elevated, it creates a VSS snapshot of the volume containing the root directory.
4. File operations are performed through the VSS snapshot, allowing access to locked files.
5. After manifest creation, the VSS snapshot is automatically cleaned up.

**:Elevation Handling**
The `ElevationHelper` class manages the elevation process:
- `IsElevated()`: Checks if the current process has administrator privileges
- `RequiresElevation()`: Determines if VSS mode requires elevation
- `RestartElevatedAsync()`: Restarts the application with elevated privileges

**:VSS Components**
- `VssSnapshotManager`: Creates and manages VSS snapshots, implementing `IDisposable` for proper cleanup
- `VssPathResolver`: Translates original file paths to their corresponding paths in the VSS snapshot
- `VssSnapshotException`: Custom exception type for VSS-related errors
- `VssErrorCode`: Enum defining error codes for VSS operations

**:Security Considerations**
- VSS operations require administrator privileges
- The elevation request is explicit and requires user approval
- VSS snapshots are automatically cleaned up after use
- Only the volume containing the root directory is snapshotted

**:Error Codes**
- `100 (ElevationRequired)`: VSS mode requires administrator privileges
- `101 (VssNotAvailable)`: VSS is not available on this system
- `102 (SnapshotCreationFailed)`: Failed to create the VSS snapshot
- `103 (VolumeNotSupported)`: The volume does not support VSS snapshots
