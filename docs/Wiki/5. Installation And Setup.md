## Overview

Verity is a high-performance file integrity verification and manifest creation tool built on .NET 9.0 with C# 13.0. It supports parallelized processing, rich terminal UI via Spectre.Console, and automation-friendly output with distinct exit codes and machine-readable TSV reports. This document provides comprehensive guidance for installing and setting up Verity across different platforms using various methods including pre-built binaries, self-contained executables, and source compilation.

The tool is designed to be executed as a single, native AOT-compiled executable on Windows, eliminating external .NET runtime dependencies. For development and customization, it can be built from source using provided build scripts for both Windows (PowerShell) and Unix-like systems (Bash).

## Prerequisites

Before installing or building Verity, ensure the following prerequisites are met:

- **.NET 9.0 SDK**: Required for building from source or running in development mode. The project targets `net9.0` as specified in the `.csproj` file.
- **PowerShell 5.1+ or PowerShell Core**: Required for executing the Windows build script (`build.ps1`).
- **Bash-compatible shell**: Required for Unix-like systems to run the `build.sh` script.
- **Git**: Required for version control integration and proper functioning of Nerdbank.GitVersioning.
- **Cake Build Tool**: Automatically restored via `dotnet tool restore`, used for orchestrating the build process.
- **Windows Volume Shadow Copy Service (VSS)**: Required for VSS functionality, available on Windows 10/Server 2016 and later.
- **Administrative privileges**: Required when using VSS functionality, as snapshot creation requires elevated permissions.

The project uses Native AOT publishing (`<PublishAot>true</PublishAot>`) to generate a self-contained executable, which requires the .NET 9.0 SDK with Native AOT support.

## Installation Methods

### Pre-built Binaries

Pre-built binaries for Verity may be available through release packages on the project's GitHub repository. These are typically distributed as ZIP archives containing the fully compiled executable and any necessary dependencies.

To use pre-built binaries:
1. Download the latest release package from the GitHub releases page.
2. Extract the archive to a desired installation directory.
3. Add the directory to your system PATH for global access (optional).
4. Verify installation by running `Verity.exe --help`.

Note: As of current documentation, direct download links are not provided; users are encouraged to build from source or use the AOT-compiled output from the build process.

### Self-contained AOT-compiled Executables

Verity is configured to produce self-contained, Native AOT-compiled executables for Windows. This means the resulting binary includes the entire runtime and does not require a separate .NET installation on the target machine.

The AOT compilation is enabled in the project file via:
```
xml
<PublishAot>true</PublishAot>

```

After building, the executable is packaged in a ZIP file located at:
```

artifacts\Verity-v<version>.zip

```

This ZIP file contains a single `Verity.exe` that can be run directly on compatible Windows systems without any additional setup.

### Building from Source

Building Verity from source allows for customization, contribution, and platform-specific compilation. The process involves restoring dependencies, compiling the code, and generating the final executable.

The primary steps are:
1. Clone the repository
2. Install .NET 9.0 SDK
3. Run the appropriate build script (`build.ps1` for Windows, `build.sh` for Unix-like systems)

The build process leverages Cake (C# Make) as the build automation system, which is restored and executed via the .NET CLI.

## Platform-specific Setup

### Windows Installation via PowerShell

On Windows systems, use the provided PowerShell script `build.ps1` to build and install Verity.

**Step-by-step instructions:**

1. Open PowerShell with sufficient permissions (Administrator rights may be needed if installing globally).
2. Navigate to the repository root directory:
   ```
powershell
   cd D:\devel\Verity
   
```
3. Execute the build script:
   ```
powershell
   ./build.ps1
   
```
4. Upon successful completion, locate the output in the `artifacts` directory:
   ```

   artifacts\Verity-v1.2-alpha.zip
   
```
5. Extract the ZIP file to a permanent location (e.g., `C:\Program Files\Verity`).
6. Optionally, add the installation directory to your system PATH.

**Script functionality breakdown:**
- Sets error handling to stop on any failure (`$ErrorActionPreference = 'Stop'`)
- Changes working directory to script location
- Disables .NET first-time experience, telemetry, and logo display
- Restores required .NET tools (including Cake)
- Invokes Cake build with all passed arguments

### Unix-like Systems Installation via Shell Script

For Unix-like systems (Linux, macOS), use the `build.sh` script to compile and package Verity.

**Step-by-step instructions:**

1. Open a terminal with bash or compatible shell.
2. Navigate to the repository root:
   
```bash
   cd /path/to/Verity
   ```

3. Make the script executable (if needed):
   
```bash
   chmod +x build.sh
   ```

4. Run the build script:
   
```bash
   ./build.sh
   ```

5. After successful build, find the output in the `artifacts` directory:
   
```
   artifacts/Verity-v1.2-alpha.zip
   ```

6. Extract to a suitable location (e.g., `/opt/verity` or `~/bin/verity`).
7. Add to PATH if desired:
   
```bash
   export PATH="$PATH:/opt/verity"
   ```


**Script functionality:**
- Enables strict mode (`set -euox pipefail`)
- Changes to script directory
- Sets .NET environment variables to disable telemetry and first-run prompts
- Restores .NET tools
- Executes Cake build with all arguments

Note: While the build will succeed on Unix systems, the primary output is optimized for Windows due to Native AOT configuration. Cross-platform AOT publishing would require additional configuration.

## Environment Configuration

### PATH Setup

To make Verity accessible from any location in the terminal, add its installation directory to the system PATH.

**Windows (PowerShell):**
```
powershell
# For current user
[Environment]::SetEnvironmentVariable("PATH", "$env:PATH;C:\Program Files\Verity", "User")

# Then reload environment
$env:PATH = [Environment]::GetEnvironmentVariable("PATH","User") + ";" + [Environment]::GetEnvironmentVariable("PATH","Machine")

```

**Unix-like Systems (Bash):**
```
bash
# Add to ~/.bashrc or ~/.profile
echo 'export PATH="$PATH:/opt/verity"' >> ~/.bashrc
source ~/.bashrc

```

### .NET Runtime Environment Variables

The build scripts configure several .NET environment variables to streamline the build process:

- `DOTNET_SKIP_FIRST_TIME_EXPERIENCE=1`: Skips the first-run setup wizard and package cache initialization.
- `DOTNET_CLI_TELEMETRY_OPTOUT=1`: Disables telemetry data collection during CLI operations.
- `DOTNET_NOLOGO=1`: Suppresses the .NET logo and version banner in command output.

These settings improve build performance and reduce unnecessary output, especially in automated environments.

## Version Management and Changelog

### Nerdbank.GitVersioning with version.json

Verity uses [Nerdbank.GitVersioning](https://github.com/dotnet/Nerdbank.GitVersioning) for automated version management based on Git commit history and branch names.

The configuration is defined in `version.json`:


```json
{
  "$schema": "https://raw.githubusercontent.com/dotnet/Nerdbank.GitVersioning/main/src/NerdBank.GitVersioning/version.schema.json",
  "version": "1.2-alpha",
  "assemblyVersion": {
    "precision": "revision"
  },
  "publicReleaseRefSpec": [
    "^refs/heads/main$",
    "^refs/heads/v\\d+\\.\\d+$"
  ],
  "cloudBuild": {
    "buildNumber": {
      "enabled": true
    }
  }
}
```


**Key settings:**
- **Base Version**: `1.2-alpha` serves as the base version.
- **Assembly Version Precision**: Set to "revision" for detailed version tracking.
- **Public Release Branches**: Only commits on `main` or branches matching `vX.Y` format trigger public release versioning.
- **Cloud Build Integration**: Enables build number generation in CI/CD environments.

This system automatically calculates semantic versions based on Git history, eliminating manual version updates and ensuring consistency across builds.

### Changelog Generation with cliff.toml

The project uses `git-cliff` for automated changelog generation based on conventional commit messages.

Configuration in `cliff.toml` includes:

- **Conventional Commits Parsing**: Commits are categorized by type (feat, fix, docs, etc.).
- **Template-based Output**: Uses Tera templates to format the changelog header, body, and footer.
- **Release Tag Pattern**: `v[0-9]+\.[0-9]+` identifies release tags.
- **Commit Grouping**: Organizes changes into sections like "Features", "Bug Fixes", "Documentation", etc.
- **Post-processing**: Replaces issue references with GitHub links.

Example commit parsers:

```toml
{ message = "^feat", group = "Features" }
{ message = "^fix", group = "Bug Fixes" }
{ message = "^doc", group = "Documentation" }
```


To generate a changelog:

```bash
git-cliff --config cliff.toml --output CHANGELOG.md
```


This produces a well-structured, human-readable changelog that reflects the project's development history.

## Verification and Troubleshooting

### Successful Installation Verification

After installation, verify Verity is working correctly:

**Check version:**

```bash
Verity.exe --version
```


**Display help:**

```bash
Verity.exe --help
```


**Run a simple verification:**

```bash
Verity.exe verify --help
```


Expected output should display the command syntax, available options, and no error messages. The executable should return exit code `0` for successful commands.

### Common Installation Issues

#### Permission Errors
- **Symptom**: "Access denied" when writing to directories.
- **Solution**: Run PowerShell or terminal as administrator, or choose a user-writable installation directory.

#### Missing Dependencies
- **Symptom**: "dotnet tool restore" fails with package download errors.
- **Solution**: Ensure internet connectivity, check NuGet source configuration, or manually install Cake:
  
```bash
  dotnet tool install Cake.Tool --version 3.0.0
  ```


#### Platform Compatibility
- **Symptom**: AOT-compiled executable fails to run on target Windows system.
- **Solution**: Ensure target system meets .NET 9.0 requirements. Consider building for specific runtime identifiers if needed.

### Build Failure Troubleshooting

#### .NET SDK Not Found
Ensure .NET 9.0 SDK is installed:

```bash
dotnet --list-sdks
```

Look for a `9.0.x` version. If missing, download from [.NET downloads](https://dotnet.microsoft.com/download).

#### Tool Restore Failures
Clear NuGet cache and retry:

```bash
dotnet nuget locals all --clear
./build.ps1
```


#### Cake Execution Errors
Check Cake version compatibility. The build may require a specific version declared in `global.json` (not present in current project).

### Execution Problems

#### Missing Runtime Components
Even with AOT compilation, some system libraries may be required. Ensure Windows system is up to date.

#### Antivirus Interference
Some antivirus software may block AOT-compiled executables. Add an exclusion for the Verity directory if needed.

#### Long Path Issues on Windows
If processing files with very long paths, enable long path support in Windows Group Policy or registry.

### Volume Shadow Copy Service Support

Verity now supports Volume Shadow Copy Service (VSS) for creating point-in-time snapshots of volumes, allowing file integrity verification even when files are locked by other processes.

**Key Features:**
- **VSS Integration**: Uses AlphaVSS library to create and manage volume snapshots
- **Elevation Handling**: Automatically detects when administrative privileges are required
- **Snapshot Management**: Creates, uses, and cleans up VSS snapshots automatically
- **Path Resolution**: Maps original file paths to their snapshot equivalents

**Usage:**
To use VSS mode, add the `--use-vss` flag to your command:

```bash
Verity.exe verify manifest.sha256 --use-vss
```


**Requirements:**
- Windows 10/Server 2016 or later
- Administrative privileges (required for VSS operations)
- Sufficient disk space for shadow copies

**Error Codes:**
When VSS operations fail, Verity returns specific error codes:
- `100`: ElevationRequired - Administrative privileges are required
- `101`: VssNotAvailable - VSS service is not available on this system
- `102`: SnapshotCreationFailed - Failed to create the VSS snapshot
- `103`: VolumeNotSupported - The volume does not support VSS snapshots

**Implementation Details:**
The VSS functionality is implemented through:
- `VssSnapshotManager`: Manages the lifecycle of VSS snapshots
- `VssPathResolver`: Resolves original file paths to their snapshot equivalents
- `ElevationHelper`: Handles privilege escalation when needed
