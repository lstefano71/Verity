## Introduction
This document provides comprehensive documentation for the common command-line options shared across all commands in the Verity application. These options control fundamental aspects of execution including parallelism, I/O performance, output clarity, and logging verbosity. The analysis is based on direct examination of the source code and project documentation, focusing on the implementation details in Program.cs, VerificationService.cs, and related utility classes.

## Common Options Overview
The Verity application implements a consistent set of command-line options across its three main commands: `verify`, `create`, and `add`. These options are designed to provide fine-grained control over performance characteristics and output behavior. Based on the README.md documentation and code analysis, the common options include:

- **`--threads <number>`**: Controls the degree of parallelism for file processing operations
- **`--include <patterns>`** and **`--exclude <patterns>`**: Glob pattern filters for file selection
- **`--show-table`**: Forces display of diagnostic information even when no issues are found
- **`--tsv-report <file>`**: Specifies output destination for machine-readable error reports
- **`--root <directory>`**: Sets the root directory for file operations
- **`--algorithm <name>`**: Specifies the hashing algorithm to use (SHA256, MD5, SHA1)
- **`--vss`**: Enables Volume Shadow Copy Service mode for accessing locked files (requires elevation)

Notably, while the documentation objective mentioned verbosity (-v, --verbose) and quiet/no-progress options, the codebase analysis reveals that explicit verbosity levels and quiet modes are not implemented. Instead, output formatting is controlled through the `--show-table`, `--tsv-report`, and progress display mechanisms.

## CliOptions Record Structure
The common options are encapsulated in the `CliOptions` record structure defined in Models.cs. This immutable data structure serves as the central configuration container passed between components.


```csharp
public record struct CliOptions(
    FileInfo ChecksumFile,
    DirectoryInfo? RootDirectory,
    string Algorithm,
    FileInfo? TsvReportFile = null,
    bool ShowTable = false,
    string[]? IncludeGlobs = null,
    string[]? ExcludeGlobs = null,
    bool UseVss = false
);
```


The `CliOptions` record includes the following properties:
- **ChecksumFile**: Required FileInfo object representing the manifest file path
- **RootDirectory**: Optional DirectoryInfo for the operation root (defaults to manifest directory)
- **Algorithm**: String specifying the hashing algorithm (case-insensitive)
- **TsvReportFile**: Optional FileInfo for machine-readable error report output
- **ShowTable**: Boolean flag to force diagnostic table display (defaults to false)
- **IncludeGlobs**: Optional array of glob patterns for file inclusion
- **ExcludeGlobs**: Optional array of glob patterns for file exclusion
- **UseVss**: Boolean flag to enable Volume Shadow Copy Service mode (defaults to false)

These options are bound to command-line arguments through ConsoleAppFramework, which automatically maps the method parameters in Program.cs to the corresponding command-line flags. The framework handles type conversion and validation, with default values applied when options are omitted.

## Thread Count Configuration

### Impact on Performance
The `--threads` option controls the number of parallel worker threads used for file processing operations. This parameter has significant performance implications depending on the storage type and system configuration:

- **SSD Storage**: Higher thread counts (8-16+) can maximize throughput by keeping multiple I/O operations in flight
- **HDD Storage**: Moderate thread counts (4-8) are typically optimal to avoid excessive seek overhead
- **CPU-Bound Operations**: Thread count should align with available processor cores to prevent context switching overhead

The default value is set to `Environment.ProcessorCount`, which provides a reasonable baseline for most systems. The parameter is optional and nullable in the command methods, allowing the application to fall back to the system default when not specified.

### Worker Allocation in VerificationService
The thread count parameter directly influences the worker allocation strategy in the VerificationService class. When `VerifyChecksumsAsync` is called, the `parallelism` parameter (derived from the `threads` option) determines the number of concurrent consumer tasks:

``mermaid

A["Command Execution\n(verify/create/add)"] --> B["Parse CLI Options\ninto CliOptions record"]
B --> C["Extract threads parameter\nor use Environment.ProcessorCount"]
C --> D["Call RunVerification/RunCreate/RunAdd\nwith thread count"]
D --> E["VerificationService.VerifyChecksumsAsync\n(parallelism parameter)"]
E --> F["Create Bounded Channel\nsize: parallelism * 2"]
F --> G["Spawn parallelism\nnumber of consumer tasks"]
G --> H["Each consumer uses\nIncrementalHash instance"]
H --> I["Process files from channel\nwith progress reporting"]

```

The implementation uses a producer-consumer pattern with two channels:
- **Job Channel**: Bounded channel with capacity `parallelism * 2`, preventing excessive memory usage
- **Result Channel**: Unbounded channel for collecting verification results

The number of consumer tasks is explicitly set to the parallelism value, with each task running on a separate thread. This design ensures that the thread count directly controls the degree of parallelism while maintaining memory efficiency through bounded buffering.

## Buffer Size Optimization

### Performance Implications
The application implements intelligent I/O buffer sizing through the `FileIOUtils.GetOptimalBufferSize` method, which dynamically adjusts buffer sizes based on file size:

```
csharp
public static int GetOptimalBufferSize(long fileSize)
{
    const int smallFileThreshold = 64 * 1024; // 64KB
    const int defaultBufferSize = 4096; // 4KB
    const int largeFileBufferSize = 1 * 1024 * 1024; // 1MB
    return (fileSize > smallFileThreshold) ? largeFileBufferSize : defaultBufferSize;
}

```

This optimization provides significant performance benefits:
- **Small Files (<64KB)**: Uses 4KB buffers to minimize memory overhead
- **Large Files (>64KB)**: Uses 1MB buffers to maximize read throughput
- **Adaptive Behavior**: Automatically optimizes for file size distribution

The buffer size is applied when creating FileStream instances with asynchronous I/O options, ensuring optimal performance for both sequential and random access patterns.

### Memory Pressure Considerations
While large buffers improve I/O performance, they can create memory pressure when processing many large files concurrently. The current implementation balances this by:
- Using `ArrayPool<byte>.Shared` to rent and return byte arrays, reducing GC pressure
- Limiting concurrent file processing through the bounded job channel
- Applying buffer size decisions on a per-file basis rather than globally

However, users processing extremely large numbers of large files may encounter memory pressure. In such cases, reducing the thread count can help mitigate memory usage, as fewer files are processed simultaneously.

## Output Formatting Controls

### Quiet Mode for Scripting
Although explicit quiet or no-progress options are not implemented, the application provides several mechanisms for script-friendly output:

1. **TSV Report Output**: The `--tsv-report` option directs machine-readable error reports to a file instead of stderr
2. **Exit Codes**: Distinct exit codes enable reliable script decision-making:
   - `0`: Success (no warnings/errors)
   - `1`: Warning (warnings, no errors)
   - `-1`: Error (errors found)
   - `-2`: Canceled by user

3. **Conditional Table Display**: The diagnostic table is only shown when issues are found, unless `--show-table` is specified

For fully quiet operation in scripts, users can combine `--tsv-report` with output redirection:
```
bash
Verity.exe verify manifest.sha256 --tsv-report errors.tsv > nul 2> nul

```

### Progress Display Management
The application uses Spectre.Console for rich terminal output, including live progress bars and status updates. While there is no explicit `--no-progress` flag, progress display can be controlled through:

- **`--show-table`**: Forces display of the diagnostic table regardless of outcome
- **Output redirection**: Redirecting stdout/stderr can suppress terminal UI elements
- **TSV reporting**: Machine-readable output complements the human-readable terminal UI

The progress display is implemented using Spectre.Console's Progress and Status components, which automatically detect terminal capabilities and adjust output accordingly.

## Verbosity and Debugging
The current implementation does not include traditional verbosity levels (-v, --verbose flags). However, debugging information can be obtained through:

1. **Detailed Error Reports**: The TSV output format provides comprehensive error details
2. **Exception Information**: Warning-level results include exception messages when file reading fails
3. **Progress Events**: The application raises FileStarted, FileProgress, and FileCompleted events that could be leveraged for verbose logging

For debugging purposes, users can:
- Examine the TSV report for detailed error information
- Monitor the terminal output for progress and status updates
- Use the `--show-table` option to force display of diagnostic information

Future enhancements could include explicit verbosity levels to provide more granular control over output detail.

## VSS Support and Elevation Handling
The application now supports Volume Shadow Copy Service (VSS) mode through the `--vss` command-line option, enabling access to locked files by creating volume snapshots.

### VSS Snapshot Lifecycle
When the `--vss` option is specified, the application follows a specific lifecycle for VSS operations:
```

The VSS snapshot lifecycle includes:
1. **Snapshot Creation**: A shadow copy of the volume is created using AlphaVSS library
2. **Path Resolution**: File paths are translated to snapshot paths using VssPathResolver
3. **File Processing**: All file operations are redirected to the snapshot
4. **Cleanup**: The snapshot is automatically deleted when processing completes

## Usage Examples

### Quiet Mode for Scripting

```bash
# Run verification and capture errors in TSV format, suppressing terminal output
Verity.exe verify backup.sha256 --tsv-report verify-errors.tsv > nul 2> nul

# Check exit code in batch script
if %errorlevel% equ 0 (
    echo Verification successful
) else if %errorlevel% equ 1 (
    echo Verification completed with warnings
) else (
    echo Verification failed
)
```


### High Verbosity for Debugging

```bash
# Show detailed diagnostic table even when no issues are found
Verity.exe verify backup.sha256 --show-table

# Include TSV report for machine processing
Verity.exe verify backup.sha256 --show-table --tsv-report debug-report.tsv
```


### Thread Tuning for Different Storage Types

```bash
# Optimize for SSD with high parallelism
Verity.exe verify backup.sha256 --threads 16

# Conservative threading for HDD
Verity.exe verify backup.sha256 --threads 4

# Create manifest with custom threading and filtering
Verity.exe create archive.sha256 --root D:\data --threads 8 --include "*.jpg;*.png" --exclude "*.tmp"
```


### VSS Mode for Locked Files

```bash
# Verify files including locked system files using VSS
Verity.exe verify system.sha256 --vss --root C:\Windows

# Create manifest of database files that are normally locked
Verity.exe create database.sha256 --vss --root C:\ProgramData\MySQL --include "*.ibd;*.frm"
```

## Troubleshooting Common Issues

### Excessive Log Output
**Issue**: Terminal output is too verbose for automated processing
**Solution**: Use `--tsv-report` to redirect machine-readable output to a file and redirect stdout/stderr:

```bash
Verity.exe verify manifest.sha256 --tsv-report errors.tsv > output.log 2>&1
```


### Memory Pressure from Large Buffers
**Issue**: High memory usage when processing many large files
**Solution**: Reduce thread count to limit concurrent file processing:

```bash
Verity.exe verify large-archive.sha256 --threads 4
```

This reduces the number of simultaneous 1MB buffers from (default) CPU count to 4.

### Performance Bottlenecks
**Issue**: Suboptimal performance on specific storage types
**Solutions**:
- **SSD**: Increase threads to 1.5-2x CPU count
- **HDD**: Reduce threads to 2-4 to minimize seek overhead
- **Network Storage**: Use moderate thread count (4-8) and monitor for timeouts

### Missing Diagnostic Information
**Issue**: No output when verification succeeds
**Solution**: Use `--show-table` to force display of summary information:

```bash
Verity.exe verify manifest.sha256 --show-table
```


### VSS Operation Failures
**Issue**: VSS operations fail with elevation errors
**Solution**: Ensure the application is run with administrator privileges:

```bash
# Run as administrator or allow elevation prompt
Verity.exe verify backup.sha256 --vss
```

## Conclusion
The Verity application provides a robust set of common options that effectively balance usability, performance, and automation needs. The `CliOptions` record structure centralizes configuration, while ConsoleAppFramework handles command-line binding seamlessly. Key strengths include:

- **Adaptive Performance**: Dynamic buffer sizing and configurable parallelism optimize for different workloads
- **Scripting Support**: Machine-readable TSV output and reliable exit codes enable automation
- **Resource Management**: Bounded channels and array pooling prevent excessive memory usage
- **VSS Integration**: Volume Shadow Copy Service support enables access to locked files with proper elevation handling

While explicit verbosity controls are absent, the combination of TSV reporting, exit codes, and conditional output display provides sufficient control for most use cases. Users can optimize performance by tuning thread counts based on their storage characteristics and monitoring memory usage when processing large file sets.

The architecture demonstrates effective use of modern C# features including records, async/await, and producer-consumer patterns with channels, resulting in a high-performance, maintainable codebase.
